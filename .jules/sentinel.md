## 2026-08-04 - Race Conditions & UnboundLocalError in Challenge Transactions
**Vulnerability:** In concurrency-sensitive views like challenge joining or rematching, conducting balance checks or maximum locked balance percentage checks using cached or thread-local `request.user` fields before calling `select_for_update()` introduces a race condition (TOCTOU). Furthermore, referencing `user` before fetching it from the database triggers an `UnboundLocalError`.
**Learning:** Checking state on `request.user` without acquiring a row-level database lock via `select_for_update()` inside `transaction.atomic()` opens up parallel request exploits, potentially leading to over-locking of balances or negative wallet balances.
**Prevention:** Always retrieve and lock the target user via `select_for_update()` at the *very beginning* of the atomic transaction block before executing any balance, limit, or trust score checks. Use the locked `user` instance for all subsequent state operations.
