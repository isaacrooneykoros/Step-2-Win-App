# Sentinel Security Journal

## 2026-07-27 - Atomic Locking Order and Pre-Check Race Conditions in Financial Views
**Vulnerability:** Race conditions in views handling user wallet balance and challenge locking (e.g., `join_challenge`). Limit checks (such as `MAX_LOCKED_BALANCE_PERCENT` and available balance checks) were performed on non-locked user data or before calling `select_for_update()`, making it possible for a user to issue concurrent requests and bypass balance limits, leading to potential negative balances or exceeding lock restrictions. Additionally, accessing `user` before it was retrieved from database caused an `UnboundLocalError`.
**Learning:** In Django, when executing within `transaction.atomic()`, database locking via `select_for_update()` must occur at the very beginning of the transaction block and definitely before any validation rules (such as checking if a user has sufficient balance) are evaluated. Performing checks on cached or stale `request.user` instances leaves the application open to race conditions because multiple concurrent requests can pass the check before any of them lock and deduct the balance.
**Prevention:** Always structure transactional business logic as follows: first open a transaction block (`transaction.atomic()`), second fetch the up-to-date user instance and lock it via `select_for_update()`, third perform all validation and balance limit checks using the locked user instance, and only then proceed with state changes (such as deductions and model saves).
